# 初始化与新增成员中断恢复 · 2026-11-06

开发版本仍为 `0.2.0a2.dev0`。本单元接续窗口关闭修复 `6a0799c`，实现评审中称为 F4 的本地成员迁移恢复。没有改变全自动管理和额度业务规则，也没有连接真实平台。

## 实际改动

1. **先保存完整计划，再改账本。** 共享责任登记升级为 schema 3，保存当前计划的 ID、原成员与目标成员、每个成员的原规范路径、账户与操作历史摘要、精确迁移前后 anchor，以及完整旧操作清单。原 operation ID、目标摘要、导入顺序和代次在计划建立时固定。
2. **正常执行与恢复共用一个入口。** 初始化、扩员和中断恢复都经过相同的共享独占事务：全员预检 → 登记成员与原操作 → 逐账本写本地见证 → 全员核对 → 共享状态改为 ready。无网络操作或人工等待发生在该事务中。
3. **逐账本原子写入、按原计划向前补齐。** 每本账本将目标 anchor 与本计划审计写在同一个 SQLite 事务内。已完成的成员必须具有精确匹配的计划审计；未完成的成员必须仍处于精确原状态。中断后重试会验证已完成成员，只补齐尚未完成成员，不复制旧操作或重复审计。
4. **保留全部能确认来源的旧责任。** 迁移使用完整 action history，不能使用界面每个目标只显示最新一条的投影。不同原账本对同一个目标的独立旧 operation 都保留；同一本账本同一目标有多笔未决时，目前明确阻断，不能静默丢掉较早的一笔。多个账本重复使用同一 operation ID 时同样拒绝猜测归属。计划完成并进入 ready 只表示名册、见证与旧责任导入一致；导入的未决操作仍保留责任，全部可信结清之前不能领取新的删除许可。
5. **恢复入口受原计划限制。** 重新加载原成员、正常管理入口检查时，可恢复具有完整计划的中断。复制到其他路径的账本不能接管，未知成员不会自动扫描加入，旧计划的迟到执行不能覆盖新计划。恢复本身不签发删除许可，不重新发送删除。
6. **兼容旧协议但不补造证据。** 健康 schema 1/2 登记可显式升级，保留 epoch、已有责任和检查点；schema 2 已保存的提交前恢复证据继续保留。旧 initializing 状态没有完整计划时仍阻断，旧的逐步注册和直接完成入口不能绕过计划。

代码分工：`responsibility_registry.py` 管理共享计划与互斥；`membership_recovery.py` 负责本地身份、历史、见证和审计；`responsibility_gate.py` 将原来的初始化、扩员及生命周期恢复接到同一个协议。

## 改动理由

旧实现将共享登记、多个本地账本 anchor 和完成标记分开写入。中途退出可能留下 X 已更新、Y 未更新、Z 尚未登记路径的混合状态。只凭当前成员列表重算名册，无法证明没有遗漏原计划里的成员或旧操作；简单“取消初始化状态”会失去保护。

持久计划记录的是中断前已经确定的意图。恢复只验证并继续这份意图，不从今天剩下的文件推测昨天想做什么。共享事务失败可以回滚共享行，而本地已提交见证保留；两者之间的差异由计划里的 before/target 和审计精确解释。

本次采纳独立评审关于完整计划、正常路径与恢复共用互斥、先全员预检、旧恢复者隔离和正向恢复闭环的建议。没有引入时间租约，也没有为每枚 Key 增加审批。

DSH 对 F2 提出的“`unknown/unknown_result` 一律不走未发送恢复”建议未直接采纳：当前 UI 在许可尚未发出时也可能记录此状态；状态名称不能代替发送证据。提交前恢复仍要求原回执、已保存的前序检查点、相同独占隔离和无本地发送边界见证。旧协议无法证明的情况、已跨过发送边界的情况继续阻断；已有 F1/F2 回归继续保留。

App 第一轮有一项测试断言失败：合法只读费用读取新增 `snapshot`，但夹具错误要求所有事件完全不变。诊断确认唯一新增项是该快照后，将断言收窄为除只读快照外全部事件及全部成员 anchor 不变，5 项复测通过；没有修改生产代码来绕过失败。

3 项进程退出测试用独立子进程 `os._exit(73)`，分别在初装首本本地提交后、初装全部本地提交后但共享提交前、扩员部分本地提交后退出。新进程经实际 SQLite journal 恢复，继续同一计划，并验证后续两个普通操作使用独立原回执、依次通过真实 Gate。

完整回归没有 `invalid command name`；仍观察到此前记录的 ttk `ThemeChanged` 警告，不能称所有 Tk 警告均已消失。`git diff --check` 通过。GitHub 完整 CI 由本单元提交触发，结果以该固定提交的 Actions 为准；本节没有提前将 CI 计为通过。

本地原始日志位于开发工作区外层的 `validation/membership-local-tests.log`、`membership-gate-process-first.log`、`membership-recovery-workflow-final.log`、`membership-full-final.log`，不随源码上传。新测试和合成夹具随源码备份，可在无真实账号的 Windows 环境重复运行。

假浏览器独立计数许可接受、许可消费和模拟发送，不能将方法调用次数当作真实平台删除成功。完整回归包含定向测试，不能把各行数量相加作为独立总数。

## 仍未解决或未验证的事项

- 没有原持久计划的旧迁移、原成员文件缺失、原路径移动、账户或关键历史改变、未知名册或检查点，仍拒绝自动恢复。不会通过扫描、删成员、重置登记或手改数据库解锁。
- 共享数据库和外部锚点是两个文件。若外部锚点已经发布、数据库提交却未完成，文件对不一致仍阻断；初次创建在完整计划提交之前中断也可能留下不完整文件。本单元不声称修复这些缺少一致原证据的状态。
- 单本账本同一目标多笔旧未决目前仅明确诊断和保留，尚未实现逐笔恢复界面；这不会被当作“已迁移完成”。
- 整体历史共同回滚、旧客户端、其他 Windows 用户或其他设备仍不在本机协作协议的保证范围内。
- 子进程直接退出验证不是断电、磁盘故障或文件系统耐久性认证；多实例并发仍可能收到短暂占用错误，应保留证据并稍后重试。
- 真实账号、真实正额度跨线后的周期自动撤销、Excel/WPS 真实导入、长期运行及同机其他操作干扰尚未完成交付验收。本轮不进行这些操作。
- 已发布的 `0.2.0a1` 便携包未被覆盖。源码备份和离线通过不等于可以投入真实使用。

下一轮建议独立检查：局部成员文件回退与旧计划审计组合、升级前后未决责任是否完整、恢复完成后实际自动管理与强制入口是否各只执行一次，以及原锚点与数据库文件对失配时的明确人工恢复说明。只有完成开发、构建和必要交付验证，才安排真实实战。
