# 4B 产品接入进展、失败记录与下一步评审

日期：2026-11-13 开始，2026-11-14 收尾（UTC+8）。对象：独立开发支线 `0.2.0a3.dev0`。旧可用 dev3、旧实验、旧包与真实账本不在本轮修改范围内。许可证继续使用 Apache-2.0。

**目前不能交付为“解压双击就能持续自动管理”的软件。4B 已经接进实际产品操作链，但真实模型的完整合成业务流程没有通过；本轮只备份开发成果，不构建或发布可用包，也不替换 dev3 做真实管理。** 本轮没有访问真实账户、付费调用或删除真实 Key。程序回归、无模型保护和合法工具调用，均不能代替实际模型完成读取与删除的证据。

## 一、实际改动

实现了程序与本地 4B 的阶段分工。程序打开通用用量页或 Key 列表页，等待公开页面就绪；4B 从完整的公开候选中选择目标、输入控件、读取按钮、菜单和确认。程序保留金额计算、额度判断、账户与完整 Tracking ID 核验、一次性提交许可、跨账本责任及原操作恢复。模型失败后没有旧脚本或 0.5B 代替它完成操作。

本地模型为 **Qwen3-4B-Instruct-2507，bartowski Q4_K_M**；引擎为固定 llama.cpp b11960 / `8642541b255bfb5dc39cd351a178be09013a55d6`，使用固定的 Qwen 官方模板。产品仍使用受约束 JSON 动作协议。后述原生工具调用只是独立只读实验，没有替换产品协议。原有 Qwen2.5-0.5B 仍仅用于诊断说明排序。

本轮同时修复实际集成中的边界问题：

- 第一次页面导航前安装网络门禁。模型触发的原始浏览器请求通过唯一的受控转发路径发送，保留原目标与正文；禁止重定向、隐式重试和失败后再次放行。该路径使用 `route.fetch(max_redirects=0, max_retries=0)` 后回填响应，不调用另一套删除器补发。
- 页面就绪不依赖目标答案；完整候选保留，公开单元格文字增加分隔。日期填写历史保留请求值、前后实际值与 `no_change`。等待、滚动、过期引用或无变化输入不冒充有效业务操作。
- 模型清理失败保留原对象与未完成状态；其他自有资源仍继续清理，不能因一个退出异常跳过浏览器和线程回收，也不能在旧模型未清理时换新模型继续管理。
- 模型初次启动或页面操作失败通过固定原因白名单传到 GUI 和诊断说明，不再误显示成账户不匹配、费用类别待适配或泛化的读取失败。初启失败保留原金额，但清除本次身份与费用核验状态，不凭空授予管理资格；IPC 同时验证动作类型和删除许可状态。
- 新建列表可在明确的首次使用流程中准备管理记录；已有身份、绑定、历史或登记残留继续走原恢复路径，不静默重建登记。
- 完成便携资产锁、相对程序目录定位、第三方许可与构建接线；旧的仅验证 0.5B 包的 portable CI 不作为本支线 4B 发布资格。本轮不产生可用包。

详细实现审查见 [集成问题与修复证据](operator-integration-review-20261113.md)，设计采纳见 [两份评审采纳记录](operator-review-disposition-20261113.md)，打包与用户流程设计见 [便携说明](operator-portable-guide.md)。

## 二、改动理由

页 GPT 的 `deepseek_4b_staged_operator_review_20261113.md` 与 DSH 的 `deepseek-4b-operator-review-2026-11-13.md` 都支持程序准备业务阶段、AI 处理页面内的动态操作，也都提醒不能把旧原型的四例局部删除成功当成完整产品通过。本轮采纳了这个分工和证据要求；评审文档里的建议并不自动变成真实账户操作或发布授权。

产品实测暴露了两种失败：先是在已经正确的日期框重复填写相同值；增加通用反馈后，仍会点击非目标 Harness 项的费用控件。r4 换成明显不同的完整合成 UUID 后也失败。因此，现有证据只能支持“**当前模型、任务、观察与协议组合，尚不能可靠完成目标识别和任务推进**”，不能把原因唯一归为 ID 太相似、字段数组、原生工具接口缺失或模型参数量不足。

这轮停止逐个失败案例追加提示词，保留全部失败，并进行两轮有固定数量上限的只读对照。它们帮助缩小下一步研究范围，却没有修复业务能力。尤其不能为了得到成功结果，由程序只留下正确目标、预先打开目标菜单，或在 AI 失败后替它删除；那将改变已经商定的 AI 操作职责。

另外，独立本地重定向实验曾观察到服务器收到两次 POST，但浏览器路由只观察到第一次；所以修复了真实发送路径，而非仅增加模型提示。这是已取得证据的工程缺陷，与模型选错控件是两个问题。

## 四、仍未解决或未验证的事项

**交付阻碍仍是实际模型业务能力。** 当前没有完整产品正向成功例；无模型保护、合法 JSON/工具调用、旧四例删除、程序回归都不能解除这个阻碍。新主诊断 20 例、新布局留出 20 例、S/N 导航职责对照、多生成 seed 稳定性和 10/30/100 枚实际模型队列均未运行，不能写成通过。真实平台、正额度消费跨线后撤销、异常结果恢复、最终 EXE 与干净机器长期运行也尚未验收。

下一步建议先研究以下有限范围，不再无上限调整同一失败案例的提示：

1. **结构化公开表格观察。** 将页面上本来可见的表头、行、完整公开 ID、控件归属、当前输入值和可用动作，以通用表格结构提供给模型。候选不能按授权目标筛选、置顶或隐藏，不能由程序计算正确 ref；对同一页面更换任务目标，观察编译结果应完全相同。先用少量冻结例比较结构表达与现有扁平文本，每例仍保留全部干扰项、乱序和 DSH 项。
2. **区分呈现问题与任务难度。** 在预先登记的合成用例中分别加入长 ID、相似 ID、日期输入、同名行、特殊管理项、菜单和二次确认，逐项比较。低难度成功只解释能力边界，不代替最终完整任务；禁止因为目标难找就在正式评判中移除干扰项。真实平台的通用控件复杂度须来自公开文档或脱敏页面结构，不能凭单个测试模板代表全部网页。
3. **评估更强模型，而非承诺 4B 必然够用。** 若在通用结构和冻结条件下仍无法可靠定位或推进，独立比较更强模型及所需内存、推理时间、包体和许可；先确定硬件与资源预算，再选择资产。参数更多或原生工具调用不保证正确性。0.5B 接管、Thinking、GPU、多模型并行均未验证，不一次同时引入。
4. **能力与保护联合通过后再打包。** 继续保持同一浏览器、原 operation、原许可与独立核实；正向成功后覆盖错误目标、低费/缺费、重复/重定向、回包丢失和关闭恢复。通过冻结的完整诊断才解锁未见留出；最终包需要自己的资产指纹与实际模型成品验收。100 枚同时到线的首末等待、p50/p95、未知隔离与资源峰值另测，不以单例耗时直接承诺吞吐或零超支。

给页 GPT 与 DSH 的本轮最小问题是：现有完整候选里能否通用地表达“目标 ID—公开行—控件”关系而不泄露正确答案；如何设计最小的任务复杂度对照；两轮只读诊断是否足以放弃这两个具体改法；更强模型对照应怎样固定条件与资源预算。请同时检查上述失败统计、原生工具多变量限制与历史重建限制。无需上传模型大文件、完整源码或任何真实账户资料。

只有这些后续证据支持后，才能把“计划中的解压双击流程”改写成“已交付且可以开始受控真实试用”。当前结论保留为开发备份。
