# 提交前中断责任恢复：进度与下一轮独立评审

日期：2026-11-06。基线：`3b8c941e12dbc2d672a1c88048032ddbc6045dd3`。

本轮是 `development/persistent-responsibility-20261106` 的开发源码备份，沿用 Apache-2.0。不是新的 Windows 发布包，也不代表生产验收通过。已发布 `0.2.0a1` 不包含本轮功能。真实平台测试继续等待使用者明确开始。

## 一、实际改动

### 1. 提交前恢复协议与精确检查点

共享责任登记升级为 schema 2，保留原 epoch、operation、目标摘要、成员与路径。每个新 claim 在共享事务内保存**该账本原来的检查点**。全局 generation 可能被其他账本的操作推进，不能用 `generation - 1` 推算原值。

两类中断现在有受限的本地恢复路径：

- F1：共享 claim 成功，但原账本尚未保存 pending。恢复补齐检查点和专用恢复审计，不补造 pending/requested，不推测姓名、金额或目标明文。
- F2：原账本保存了 pending/requested，但还未取得发送许可；例如 requested 已提交 SQLite，而日志导出失败。恢复保留原事件与原证据，追加同一 operation 的取消终态。

恢复先在共享事务内持久隔离原操作，继续占用原责任槽。随后在原账本的一个事务中写入恢复审计、终态封印（tombstone）和检查点；日志成功导出并复核后，才按原 receipt 与 recovery ID 结清。原登记、账本与阶段证据仍可验证时，可以从同一阶段继续，不重新发送；资料缺失或跨文件失配时保持阻断。

### 2. 防止旧回调与旧备份重新打开操作

旧操作的发送升级与恢复隔离使用同一 SQLite 独占事务。恢复先成功，旧升级就不能再取得许可；发送升级先成功，恢复则拒绝按未发送结清。

在发送升级之前，原账本先持久保存发送边界见证。若有人把共享登记数据库和外部锚点成对恢复到旧的 declared 快照，本地见证仍会指出该操作曾跨过发送边界。此时必须只读核实，不能用旧登记误判为未发送。

原账本在普通 `record_action()` 的写事务内检查终态封印，拒绝该旧 operation 的全部迟到回调，包括 requested、unknown 和 absent。否则迟到的 absent 可能影响后来新操作的目标绑定。界面将明确被封印的旧回调作为过期结果处理，不放进无限重试的“保存处理记录”队列。

### 3. 接入重开账本与正常工作流

重新载入原账本时，程序会尝试完成有充分证据的本地恢复。成功后刷新人员状态与处理记录，自动管理保持停止，用户仍按原流程重新读取费用、启动管理。

自动管理、强制删除都保留原入口与原规则：`-1` 跳过，零额度原规则不变，正额度要求有效费用依据，强制删除免额度条件；没有逐 Key 人工审批。恢复不会调用浏览器、平台或模型。

schema 1 的健康登记可在载入生命周期中保留身份升级；旧义务的原检查点和发送见证不凭空补造，因此旧未决义务不享有 F1/F2 自动恢复捷径。遗留“定位网页后由用户自己点击删除”的入口也不使用这条捷径。

## 二、改动理由与评审采纳

这轮参考 DSH 的 `deepseek-persistent-responsibility-next-review-2026-11-06.md` 和使用者粘贴的页 GPT 评审。两份材料帮助把“能阻止错误删除”进一步拆成“哪些情况下还能安全恢复使用”。它们提供的是待验证建议，结论由源码与测试核对。

| 建议或反例 | 本轮判断 |
| --- | --- |
| F1/F2 先持久隔离，再补本地审计，最后释放原槽 | 采纳，并验证两方向竞态 |
| 用 receipt generation 减一得到旧检查点 | 不采纳；全局序列跨账本，保存精确前值 |
| possible_send 后只因没有 dispatch 日志、进程退出就判未提交 | 不采纳；不能据此证明平台没有执行 |
| 本地 requested 导出成功后，可以恢复原发送 | 不采纳；恢复只结清旧意图，不重放删除 |
| 仅共享登记显示 declared 即可认定未授权 | 不充分；补原账本发送边界见证，覆盖成对旧备份回退 |
| F4 初始化／加入成员中断需要持久完整计划 | 采纳方向，下一独立单元实施；本轮不宣称已修复 |

SQLite 单个写事务的原子性不等于多个账本与外部锚点共同原子提交。这里仍采用分阶段持久证据，跨文件失配保持阻断。SQLite 的事务与锁规则参考[官方事务文档](https://sqlite.org/lang_transaction.html)；WAL 也不能自动提供跨数据库整体原子性，见[官方 WAL 文档](https://sqlite.org/wal.html)。Windows 互斥对象被遗弃仅说明原持有者异常结束，不证明共享业务状态有效，见[Microsoft Mutex Objects](https://learn.microsoft.com/en-us/windows/win32/sync/mutex-objects)。

## 四、仍未解决或未验证的事项

1. F4：初始化／新增成员中断仍保持 `initializing`，本轮没有自动补齐工具。下一步应在开始时持久保存完整成员变更计划，包括原路径、精确旧检查点、原见证、目标名册，以及待迁移旧责任。
2. schema 1 的旧未决、资料不足、成员丢失、路径改变或无法解释的检查点仍保守阻断，不通过清库、删成员或猜测补证解锁。
3. 已进入 possible_send，或原账本已有发送边界见证时，仍只能通过原操作的只读核实结清。没有实现远端幂等、冻结 Key 或撤回已经交给 worker 的许可。
4. 外部锚点与登记数据库写入间真正中断、两者失配后仍阻断；没有通用修复器。若所有登记、锚点和全部账本一起一致回滚，本地证据无法保证发现这种整体历史丢失。
5. 本轮工作流是实际 App 加合成平台，不能等同真实 worker 强杀、系统断电、长时间运行、跨 Windows 用户／设备或真实平台验收。
6. 之前未验收的正额度真实消费跨线、Excel/WPS 真实导入、同机干扰等仍未验收。全量测试仍出现 Tk 销毁后的 ThemeChanged 提示，本轮还观察到 `_watch_workbook` 的 after 回调已不存在提示；其与多窗口测试销毁顺序的关系尚未独立定位，不因 unittest 通过而声称已解决。
