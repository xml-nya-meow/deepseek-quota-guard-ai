## 2. 改动理由与边界

用户要的是由 AI 操作网页、程序判断额度并可靠执行管理。模型是否选择了正确控件，与浏览器实际发送几次请求，是两件必须分别验证的事。一次模型确认、一次许可消费，不能天然推出网络上只发出一次 POST。

R1 的最小修复仍要求原请求由 AI 选择的网页控件产生，程序只核对并转发这一请求。不允许程序在模型失败后补造一个删除请求，不允许更换目标，也不允许重试。这样可保留“AI 负责操作、程序负责授权与一次提交”的分工。

执行器改用受控 `route.fetch` 后，离线夹具不能继续假定请求会经过原来的最底层 loopback route。必须显式将这个发送点接到自建 loopback 后端，保持原 URL、方法、正文与一次许可语义；不能为了让验收通过而移除离线网络隔离。

费用准备也应受相同范围约束。即使重定向后的费用响应不会被本地账本接受，只要请求已经查询了其他目标或全账，仍违反“仅查询受管目标”的约束，不能仅靠最终结果校验代替发送前控制。

恢复与资格规则不因上述修改放松。费用新鲜度仍按真实采样开始计；跳转到 Key 页面、准备模型上下文不能重置 300 秒时限。未决结果保留原 operation，不能再签发新提交。

## 3. 已经运行的验证

### 3.1 Playwright 307 最小实证

使用随旧便携包附带的 Chromium，开一个无用户资料的 headless 上下文；仅启动自己创建的 `127.0.0.1` HTTP 服务，不访问 DeepSeek 或其他外部服务，不运行模型。服务行为为：

- `POST /first` 返回 `307 Location: /retry`，并允许本地试验的 CORS；
- `POST /retry` 返回 200；
- `BrowserContext.route('**/*', ...)` 只允许 `/first`，任何其他 URL 都执行 `abort`；
- 页面只调用一次 `fetch('/first', {method: 'POST', ...})`。

实际观测（省略临时端口）：

```json
{
  "arrivals": ["/first", "/retry"],
  "route_urls": ["http://127.0.0.1:<port>/first"],
  "result": 200
}
```

这证明：后台收到了两次 POST，而路由处理器只看到第一跳。它是浏览器/路由行为的最小反例，**不是对真实 DeepSeek 做了删除测试**，也不是声称该平台当前必定返回重定向。本机安装的 Playwright 生成文档 `Page.route` 也注明重定向时 handler 只针对首个 URL；此次测试进一步核对了 BrowserContext 路由的实际行为。

### 3.2 离线验收夹具单测

`tests/test_operator_fixture.py`：**16 项通过，5.124 秒**。覆盖业务 envelope、NORMAL/DSH 契约、20 个 seed 的目标乱序、按完整 ID 选择、费用范围与日期、错误删除参数拒绝、DSH 拒绝、响应丢失后的后端状态、公开 HTML 不含评分答案、严格 loopback/来源、禁止脚本 POST、浏览器来源转发、响应丢失路由结果和跨 origin 重定向拒绝。

重定向隔离单测使用两个均由测试创建的 loopback 服务，检查第二个服务收不到请求，即使保护回归也不会用真实外站检测。此组测试没有加载浏览器或模型，不代表模型决策能力验收。

### 3.3 只读审查结论

- 未发现按目标答案过滤候选或由后台评分文件指导模型。
- 模型失败没有进入旧 HTTP 删除器的正常调用路径；保留的 legacy 方法不是公开 worker 动作。
- 永久写边界可阻止普通延迟计时器产生的新 POST，但不能在未修 R1 时宣称覆盖 307/308 浏览器内部跟随。
- 未增加真实平台测试、付费请求、真实 Key 删除或旧账本修改。
