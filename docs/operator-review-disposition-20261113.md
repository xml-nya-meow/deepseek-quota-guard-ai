## 一、实际改动

新产品采用阶段分工：程序确定受管范围、日期、金额规则和当前业务阶段，只准备通用用量页或 Key 列表页；4B 从当前公开观察中选择目标、读取控件、菜单、删除入口及确认。程序仍负责金额解析、到线判断、完整 Tracking ID/账户核验、一次性提交许可、持久责任与独立结果核实。详见[便携版使用与验收边界](operator-portable-guide.md)。

4B 是 Qwen3-4B-Instruct-2507 的第三方 Q4_K_M 量化，使用固定 llama.cpp b11960 与 Qwen 官方模板。当前仍为“模板应用 + 受约束 JSON 动作”协议，不宣称使用 Qwen 原生 function calling。模型只有 `act_on_node`、`handle_dialog`、`poll_action`、`report_blocker` 四种动作；宿主准备页面、读取权威证据与业务授权不成为模型工具。0.5B 不在操作链失败时接管。

本轮同步补充了[第三方组件记录](../THIRD-PARTY-NOTICES.md)，按实际资产分别标明基础模型、bartowski 量化、官方模板、引擎和 OpenMP 的来源，保留许可原文及证据限制。

### 产品条件与旧 r2 的区别

这是一个新的产品接入条件，不能称为“原 r2 只改了一次导航”。`operator_runtime.py` 的 SYSTEM 已调整为当前已准备页面的操作，明确 READ 可接受精确的 `target_ids` 集合，并把页面阶段准备、金额、授权和核实交给宿主。动作合同增加标准日期输入控件，运行时改为可打包资产和可取消的常驻服务。产品任务/分段读取预算也须按产品自身记录，不能自动继承旧实验每例 180 秒的可比性。

模型、模板与引擎沿用锁定资源，不代表模型输入、历史和阶段状态相同。后续冻结应同时记录 SYSTEM、任务格式、候选合同、来源代码、模型及模板摘要、采样参数、绝对截止点、页面阶段和历史整理方式。修复前后结果分别保存，不合并为一批全绿。

产品 r2 的真实模型 smoke 另发现：READ 在已等于任务日期的输入框上连续八次填写相同日期，未完成业务任务。产品 r3 据此做一次通用反馈修复：历史保留 type/select 请求值及实际前后值、变化布尔值和受控状态；SYSTEM 提醒先比较当前值、不要重复无变化动作。旧引用仍剔除，全量候选不变，没有提供正确按钮或代替模型选择后续动作。**r3 实测仍未完成：先填相同日期，再选择非目标 DSH 费用控件，被范围门禁阻止。** r4 换成明显不同的完整合成 UUID，公开单元格增加分隔，仍出现同类失败。三次分别留档，不写成反馈修复已经解决模型行为。

后续进行了两轮有固定上限的只读推理诊断：目标字段数组/标量比较 8 次，以及官方原生工具接口 2 次。它们没有执行网页动作，没有修复产品能力，也没有据此把原生工具协议接入产品。具体条件和限制见第三节。

## 二、改动理由

两份评审共同支持把确定性的业务阶段交给程序，把需要适应网页结构的目标定位与交互交给 AI。这个分工针对旧实验的“正确读费后没有可靠推进到删除阶段”，也符合用户要求的 AI 代替人操作、程序保留计算和判断。

对根因采用有限结论：**旧输入、模型与合同组合在 READ 后的阶段推进不可靠。** DSH 开头“不是 JSON 约束”的措辞强于其正文所能证明；采纳正文与页 GPT 的保留意见。候选中存在导航链接、JSON 合法、上下文未截断，可排除这些具体故障，却不足以唯一排除呈现方式、阶段历史、采样或模型策略。4/4 删除诊断同时改变起点、资格来源、历史和剩余预算，不能作为纯导航因果消融。

阶段化也带来新的风险：通用导航可能自动产生越范围费用请求；多个路由叠加可能绕过提交门禁；页面准备可能误被当作证据刷新；重建模型上下文可能误建新 operation。因此优先验收实际请求边界和业务证据，不以“模型返回一个合法动作”作为全链成功。

### 必须验证的产品合同

以下是采纳的验收断言，**不是本文件宣布全部已通过**。执行结果以同版本运行记录为准。

| 类别 | 必须检查 |
| --- | --- |
| 无模型消融 | 宿主可通用导航和通用就绪观察，但不得选择目标、触发模型负责的费用查询、打开目标删除流程或产生业务写入。 |
| 换目标与乱序 | 相同公开观察下更换任务 ID，宿主页面准备与候选顺序不随答案改变；不存在、歧义、DSH 特殊项不被猜成普通 Key。 |
| READ → DELETE 证据 | 低费、缺费、类别/期间不完整、错账户、换绑定均不能产生自动删除资格；恰好达额按原规则处理。零额度与强制删除另测。 |
| 阶段时间 | 准备页面、推理、切换共享本任务绝对期限；切换不延长旧费用证据，不重置未知结果或原 operation。 |
| 路由组合 | 在第一次导航前安装实际网络边界；明确唯一发送拥有者。测试 page 路由直接放行是否绕过 context 门禁；不用的 Service Worker 等通道禁用。 |
| 重复与重定向 | 双发、并行确认、307/308、旧页/ref、弹出页和晚到模型回复不得增加实际业务写入。实际服务器到达计数与门禁消费数分开。 |
| unknown 与恢复 | 服务端写入后回包丢失仍保留原 operation；不自动重发；独立核实通过产品可取得的账户/新鲜列表路径，不读取评分后台真值。 |
| 持久化故障 | 放行前记录失败应零发送；发送后记录失败应保留责任且不重复发送；解除后合法后续任务仍可运行，不能靠永久卡死通过。 |
| 来源与日志 | 记录宿主准备、模型动作、核实、恢复等结构化来源；正式日志不存原始提示、网页全文、Cookie、Bearer 或密钥。 |

此处“同 context 的联合测试”要求同一浏览器拥有者、同一合成平台和同一原 operation。分别通过网页能力实验 A 与发送门禁 B，不等于 A+B 已联合通过。费用页自动请求全账和 page/context 路由旁路是应测反例，不写成已确认发生的真实平台行为。
