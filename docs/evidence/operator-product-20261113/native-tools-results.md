# 官方 tools 模板与原生工具调用：有界只读诊断 r1

日期：2026-11-13。结论：固定引擎能够接受本次官方模板和工具定义，返回可按原合同验证的单次工具调用；**两份观察均选择再次填写已经正确的开始日期，没有显示业务推进改善**。这不是完整能力通过。

## 一、实际改动

产品代码未改动。只在本诊断目录使用现有本地 4B 服务，比较原受约束 JSON 接入之外的原生 `/v1/chat/completions` tools 路径；不执行输出动作，不启动浏览器，不访问外网或真实平台。

沿用 r4 两份公开观察、原 `target_ids` 数组任务、原 instruction，以及上一字段诊断所重建的同一 history。模型权重、官方 Jinja、引擎、CPU 线程、上下文与生成参数保持相同，每份观察仅计划并执行一次 seed 17 推理。

原生接入的明确差异：

- SYSTEM 删除要求自定义 JSON envelope、禁止 function-call XML 的冲突语句，改为使用一个提供的函数工具。其余任务规则保留。
- 请求使用 `tools` 四函数，`parallel_tool_calls:false`，不设置 `tool_choice:required`，采用服务器默认 auto；四函数不会被服务执行。
- `act_on_node` 参数来自当前公开 schema 的全部 refs 与动作分支，不筛选正确目标。`poll_action`、`report_blocker` 沿用原参数；两份观察没有 dialog，`handle_dialog` 仍作为固定四函数接口中的静态签名列出，并说明不可用；原状态合同会拒绝在当前观察中调用它。
- 保留 user 中原 `allowed_next_action_schema`，使任务、公开事实和当前动作可用性仍可见。
- 官方模板转入 `<tools>` / `<tool_call>` 分支，服务器解析 `tool_calls`；本实验不使用原 `/completion` 的外层 `json_schema` 参数。

因此这是**多项协议接入差异的诊断**，不是只改变一个变量的模型优劣试验。参数生成、工具呈现、模板分支、endpoint 与响应解析都有变化。

## 二、改动理由

此前 `target_ids` 与 `target_id` 的八次只读比较没有改变错误动作。本次仅判断工具协议是否受固定引擎实际支持，以及在这两份观察上是否出现明显推进改善；不增加 Thinking、其他模型、目标排序或后续自动执行。

## 三、已经运行的验证

先调用 `/apply-template`，保存引擎实际返回的完整渲染结果；真实 `<tools>` 块中的四个对象与请求定义逐项相等，并包含官方 `<tool_call>` 格式。然后才调用原生 chat endpoint。每个响应严格要求恰好一个 function call，arguments 为完整、无重复字段的 JSON，最后映射回原 `validate_action(tool,args,observation)`；没有截取多调用中的第一个冒充成功。

初次模板预检出现的是**诊断器机械解析错误**：简单字符串分割先匹配了模板说明句中的空 `<tools></tools>`，没有匹配换行包围的实际工具块。该次 0 推理、2 未执行，模型已关闭；原运行器、计划、输入、渲染和失败摘要保存在 `preflight-parser-failure/`。修正提取方式后，验证实际块包含全部四函数，仍只执行原定两次推理。没有修改产品、提示或参数重试模型结果，也不把预检器错误说成服务不支持。
